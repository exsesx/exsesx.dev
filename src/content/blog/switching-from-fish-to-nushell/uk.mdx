Саме після `codex features list` я зрозумів, навіщо мені Nushell. Я хотів знайти
вимкнені можливості зі статусом `stable` або `under development` і скопіювати їх
у конфігурацію Codex як TOML. У Nu команда спершу повертає вирівняний текст.
Конвеєр перетворює його на таблицю, а потім серіалізує запис у потрібному
форматі.

Цей невеликий конвеєр переконав мене краще за черговий бенчмарк оболонок. Моя
конфігурація Fish уже була зручною: хороші доповнення, прив’язки клавіш у стилі
vi, Starship і скорочення, якими користуюся щодня. Nushell мав зберегти це
відчуття й дати мені зручніший спосіб працювати з виводом команд.

Nu залишився моєю основною оболонкою, бо його модель даних раз у раз ставала в
пригоді у звичайних командах. Тепер оболонкою входу в моєму обліковому записі
macOS є Nu, а Fish досі встановлений і навіть надає кілька доповнень, які Nu не
може згенерувати сам.

<Callout title="Перевірено локально" variant="note">
  Я перевірив приклади й конфігурацію з цієї статті 11 серпня 2026 року в
  Nushell `0.114.1` і Fish `4.8.1`. Моєю оболонкою входу є
  `/opt/homebrew/bin/nu`, а macOS знаходить каталог конфігурації Nushell у моєму
  Git-репозиторії за шляхом `~/.config/nushell`.
</Callout>

## Fish встановив високу планку

Fish уже давав мені потрібні можливості інтерактивної оболонки. Його
<SourceLink href="https://fishshell.com/docs/current/tutorial">автопідказки, підсвічування синтаксису й доповнення</SourceLink>
працювали добре, а моя конфігурація додавала Starship, історію Atuin, Zoxide,
Mise і власні прив’язки клавіш. Згенеровані інтеграції я кешував, щоб оболонка
запускалася швидко.

У конфігурації Fish я також замінив `ls` на `eza`, бо хотів бачити піктограми й
корисний порядок сортування. Цей псевдонім давав зручний для читання список. Для
подальшої фільтрації я мав розбирати текст або викликати іншу команду, яка
повертала машинозчитуваний формат.

Репозиторій із моєю конфігурацією Nushell існує з 12 серпня 2025 року. Він
залишався експериментом до 3 серпня 2026 року, коли я закомітив більший набір
змін із назвою `make Nushell viable as a daily shell`. Наступні кілька днів я
закривав прогалини в доповненнях, налаштовував кеші запуску й поведінку рядка
запрошення та вносив невеликі виправлення сумісності. Після того як ця
конфігурація витримала звичайну роботу, я змінив оболонку входу для облікового
запису.

## Рядки, з якими можна працювати далі

Команди Nu передають типізовані значення через
<SourceLink href="https://www.nushell.sh/book/pipelines.html">конвеєри</SourceLink>.
Серед цих значень можуть бути записи, списки, таблиці, дати, тривалості й розміри
файлів. Зовнішні команди й далі повертають текст або байти, тому звичні конвеєри
Unix продовжують працювати. Найбільше користі я отримую, коли команда Nu вже
повертає дані з відомою структурою.

`ls` повертає таблицю. Я можу відфільтрувати каталоги, відсортувати їх за
колонкою `modified` і вибрати потрібні колонки без розбору текстового виводу:

```nu title="Нещодавні каталоги"
ls
| where type == dir
| sort-by modified --reverse
| select name modified
```

У конфігурації Nu я навмисно залишив вбудовані `ls` і `open`. Орієнтовані на
читання команди `eza` я переніс у `lm` і `ll`, тож тепер можу вибрати між
оформленим списком і структурованими рядками. Те саме розділення працює й для
файлів. `open package.json` читає JSON як запис, а решта конвеєра працює з
полями:

```nu title="Скрипти пакета у вигляді таблиці"
open package.json
| get scripts
| transpose name command
| sort-by name
```

У Nu є вбудовані конвертери для JSON, TOML, YAML, CSV та інших форматів. Кожен
конвертер очікує сумісну структуру значення. Це точніше за твердження, наче
будь-які дані можна перетворити на будь-який формат. У форматах, якими я
користуюся, перехід від `from json` до `to toml` більше схожий на вибір типу
виводу, ніж на складання ще одного текстового конвеєра.

## Таблиця з CLI стає конфігурацією Codex

Codex виводить список можливостей як вирівняний текст. Для такого виводу я
використовую `detect columns`:

```nu title="Скопіювати вимкнені можливості Codex як TOML"
^codex features list
| detect columns --guess --no-headers
| rename name stage enabled
| update enabled { into bool }
| where stage in ['under development' stable] and enabled == false
| reduce --fold {} {|feature, config|
    $config | upsert $feature.name true
  }
| to toml
| pbcopy
```

`detect columns` перетворює текст на рядки, `rename` дає колонкам зрозумілі
назви, а `update` перетворює `enabled` із тексту на логічні значення. `where`
залишає вимкнені можливості з двома потрібними статусами. `reduce` формує один
запис, ключами якого стають назви можливостей, а `to toml` створює рядки, які я
можу вставити під `[features]` у `~/.codex/config.toml`. `pbcopy` копіює
отриманий рядок у буфер обміну macOS.

<Callout title="Не вмикайте всі можливості Codex навмання" variant="warning">
  Цей конвеєр лише демонструє можливості Nu. Можливості зі статусом
  `under development` можуть бути незавершеними або змінюватися між версіями
  Codex. Я переглядаю список і вмикаю лише те, що збираюся перевірити.
</Callout>

<SourceLink href="https://www.nushell.sh/commands/docs/detect_columns.html">`detect columns` вгадує структуру за розташуванням</SourceLink>,
тому я використовую його як адаптер для стабільного текстового виводу. Якщо CLI
підтримує JSON, я вибираю його. Тоді решта конвеєра працює з тими самими записами
й фільтрами та не залежить від пробілів між колонками.

## Паралельні оновлення без каші у виводі

Функція `update-tools` зробила Nu корисним для мене й поза однорядковими
командами. Однією командою я оновлюю Homebrew, Mise, Claude, Codex і глобальні
Skills:

```nu title="~/.config/nushell/modules/utilities.nu"
export def update-tools [] {
  let jobs = [
    {
      name: Homebrew
      commands: [
        {|| brew upgrade -y }
        {|| brew cleanup }
      ]
    }
    {
      name: Mise
      commands: [
        {|| mise upgrade }
      ]
    }
    {
      name: Claude
      commands: [
        {|| claude update }
      ]
    }
    {
      name: Codex
      commands: [
        {|| codex update }
      ]
    }
    {
      name: Skills
      commands: [
        {|| skills update -g -y }
      ]
    }
  ]

  $jobs | par-each --threads 5 { |job|
    let results = (
      $job.commands
      | each { |command|
          with-env {
            CLICOLOR_FORCE: "1"
            FORCE_COLOR: "1"
            HOMEBREW_COLOR: "1"
          } {
            do $command o+e>| complete
          }
        }
    )

    let output = (
      $results
      | get stdout
      | str join
      | str trim
    )

    let succeeded = (
      $results
      | all { |result| $result.exit_code == 0 }
    )

    let heading = if $succeeded {
      $"(ansi green_bold)✓ ($job.name)(ansi reset)"
    } else {
      $"(ansi red_bold)✗ ($job.name)(ansi reset)"
    }

    print $"\n($heading)\n($output)"
  } | ignore
}
```

Зовнішній список складається із записів. У кожному є назва для виводу й одне
або кілька замикань із командами. `par-each --threads 5` запускає п’ять записів
із завданнями паралельно, а внутрішній `each` зберігає послідовність команд у межах
одного завдання. Homebrew запускає очищення після оновлення. Mise, Claude, Codex
і Skills не чекають на цю пару.

`o+e>| complete` об’єднує потоки виводу команди, запускає замикання й повертає
структурований результат із полями `stdout` та `exit_code`. Функція з’єднує
вивід кожного завдання, перевіряє всі коди завершення й друкує для нього окремий
зелений або червоний блок. Блоки можуть з’являтися в порядку завершення, оскільки
без окремої вказівки `par-each` не зберігає порядок вхідних даних.

Fish уміє запускати фонові завдання через `&` і чекати на них. У Nu весь облік
лишається частиною тієї самої функції: завдання зберігаються як записи, команди
як замикання, а результати мають поля. Замість довгого ланцюжка
`mise upgrade && claude update && codex update` я запускаю незалежні частини
паралельно й отримую окремий
читабельний блок від кожного з п’яти інструментів.

## Я зберіг решту налаштувань термінала

Я продовжую користуватися тим самим `~/.config/starship.toml`. Fish завантажував
згенерований вивід `starship init fish`, а Nu завантажує кешований
`starship init nu`. Мій промпт із `$all`, кольори, стан Git і тривалість
виконання команд не змінилися. Інтеграції Atuin, Zoxide, Mise і Carapace теж
залишилися.

Доповнення потребували більше роботи. Я використовую вбудовані доповнення Nu для
Git і Claude, Carapace як загальний резервний варіант і невеликі окремі адаптери
для прогалин. Codex і Herdr у моїх версіях можуть генерувати доповнення Fish, але
не мають власних доповнень для Nu, тому моя система доповнень передає ці файли
через Fish. Через це я не видалив Fish і після зміни оболонки входу.

Файли `.nu` я пишу в Neovim. Увімкнення
<SourceLink href="https://www.lazyvim.org/extras/lang/nushell">додаткового модуля Nushell у LazyVim</SourceLink>
через `:LazyExtras` налаштувало мовний сервер Nushell і встановило парсер `nu`
для Treesitter. LSP добре допомагає писати функції й знаходити помилки в
замиканнях. Оскільки Neovim у мене вже був налаштований, для цього вистачило
одного перемикача.

## Я досі користуюся jq і rg

Спеціалізовані інструменти командного рядка, яким я довіряю, залишилися на своїх
місцях. Я використовую `jq` для JSON, коли його мова запитів найзручніша для
завдання або коли команда має працювати поза Nu. Через `rg` я шукаю у вмісті
файлів, а через `fd` знаходжу файли. `eza` і `bat` досі дають зручний для читання
вивід через псевдоніми.

Я вибираю Nu, коли сама оболонка знає структуру даних: у результатах `ls` і
`open`, під час роботи з датами чи розмірами файлів або у виводі CLI, який я
можу розібрати на стабільні колонки. Nu також підходить для невеликих скриптів,
де треба фільтрувати записи, паралельно виконувати роботу, перевіряти коди
завершення й серіалізувати результат.

Nushell не сумісний із POSIX, а
<SourceLink href="https://www.nushell.sh/book/default_shell.html">посібник із використання його як типової оболонки</SourceLink>
попереджає, що деякі програми розраховують на POSIX-сумісну оболонку входу.
Підтримка доповнень для зовнішніх команд різниться. `detect columns` і далі
вгадує структуру, а для кількох інструментів мені довелося зробити кеші й
адаптери. Якщо скрипт очікує Fish, я можу запустити його однією командою.

Моєю оболонкою входу досі є Nu. Для мене вирішальними стали звичайні випадки:
список каталогів, таблиця з виводу команди й набір паралельних оновлень. Я можу
переглянути колонку, відфільтрувати її та серіалізувати результат, не зводячи
дані спершу до тексту. Так я хочу щодня працювати в оболонці.
